01 / Problem

Data integration is a scientific claim, not just a format conversion.

An NMR ensemble, a molecular-dynamics trajectory, and a generated structure may all contain coordinates for the same protein. They do not automatically share the same residue numbering, experimental conditions, measurement meaning, time coverage, or allowed inference.

Flattening those sources into one table makes the software look simpler while moving the scientific mismatch out of view. Dynamics Atlas keeps the source type and comparison rules explicit. A task can proceed only through a route registered for that evidence combination.

Research engineering question

How can scientific comparison rules become executable software gates without letting an Agent invent missing mappings or approve its own route?

03 / Decisions

The collaboration keeps scientific authority outside the Agent.

Decision 01

Use data-type-specific routes.

Why
NMR ensembles, MD trajectories, database structures, and generated structures do not share one scientifically valid interpretation path.
Alternative considered
Normalize every input into one coordinate table and apply the same analysis code.
Trade-off
More adapters and route definitions are required, but each result keeps the assumptions that make it interpretable.

Decision 02

Store the decision with the output.

Why
A result is difficult to review if the source hash, residue map, route choice, and rejected alternatives disappear after execution.
Alternative considered
Keep only the final figure or summary table and rely on logs for reconstruction.
Trade-off
Receipts are larger, but a later reviewer can replay which route ran and why another route was blocked.

Decision 03

Let the Agent locate evidence, not execute the scientific route.

Why
The Agent can help find a source locator or point out a missing input. It did not reliably satisfy the full evidence and schema contract in the recorded development comparison.
Alternative considered
Allow a one-shot or tool-using Agent to canonicalize the task, choose tools, execute the route, and produce the final claim.
Trade-off
The model has less autonomy, but deterministic code retains validation, execution, veto, and final review boundaries.

Workflow and replay checks

The recorded implementation passed its harness tests, machine validations, and HSP90 output replays. These checks show that the defined routes can block invalid inputs, preserve output records, and reproduce the expected workflow behavior.

They do not establish that every scientific conclusion is correct or that the same behavior will hold for new data types without a registered route.

Exposed retrospective development packets

Why direct Agent execution was removed

Six packets were used during development. They were exposed and retrospective, so the comparison explains an architecture decision; it is not an independent Agent benchmark.

Architecture outcome The Agent was limited to locator-grounded suggestions and missing-input proposals. Deterministic components kept canonicalization, execution, veto, and final claim control.

05 / Scope

The software can enforce a comparison contract. It cannot make the contract scientifically universal.

Current scope

Research collaboration prototype

  • Registered routes and typed task records
  • Ordered compatibility and evidence gates
  • Hash-linked outputs and replay receipts
  • Agent suggestions outside execution authority

Not established

General scientific or Agent performance

  • Public harness fixtures are synthetic
  • Six development packets are not a held-out benchmark
  • No general Agent-effectiveness claim
  • No guarantee that downstream conclusions are correct

Proposed next validation

Freeze held-out comparison tasks

Evaluate locator quality, missing-gate recall, provenance completeness, unsafe allows, and expert correction time on held-out TaskPackets that were not exposed during development.

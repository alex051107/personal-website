01 / Problem

Biomedical AI needs a controlled workflow around the draft.

A model response can arrive late, use the wrong fields, repeat a previous request, or contain language that looks like an approval. If the application treats that response as the final record, a provider failure becomes a workflow failure.

CarePlan separates four responsibilities. Deterministic rules decide whether a synthetic order can proceed. The model fills a typed draft. Server code validates the fields and state transition. A reviewer account with the pharmacist role owns the final decision inside the prototype.

Design question

Which decisions must remain deterministic when a model participates in a workflow with state, permissions, retries, and human review?

02 / System

Model output enters a queue, not an approval state.

Local prototype

Stateful application path

The application design uses a backend state machine, persisted records, queued drafting, schema validation, role checks, idempotency, retry limits, and audit receipts.

The stack shown on the portfolio is Django / DRF, PostgreSQL, Celery, Redis, and OpenTelemetry.

Public surface

Deterministic control-plane harness

The public Python harness distills the workflow contract with synthetic inputs and SQLite. It demonstrates state, idempotency, schema, version, reviewer-role, and receipt behavior without publishing private repository history.

The harness does not contact a model service and is not a distributed-deployment claim.

03 / Decisions

The backend owns the decisions that must repeat exactly.

Decision 01

Run hard stops before drafting.

Why
An ineligible synthetic order should not consume a provider call or enter a review queue.
Alternative considered
Let the model interpret every order first and ask it whether the order should proceed.
Trade-off
Rules require explicit maintenance, but the same input produces the same stop before model behavior can affect it.

Decision 02

Persist state and require an expected version.

Why
A delayed provider response or second reviewer must not overwrite a newer workflow decision.
Alternative considered
Store only the final plan and infer the path from logs after a failure.
Trade-off
More transitions and version checks are stored, but stale work fails instead of silently changing the record.

Decision 03

Make repeated requests idempotent.

Why
Network retries and repeated clicks should not create multiple plans or duplicate downstream jobs.
Alternative considered
Create a new plan for every submission and deduplicate later.
Trade-off
The server must bind an idempotency key to the original payload, but a same-key retry returns the same plan while changed reuse is rejected.

Decision 04

Remove approval from the provider schema.

Why
A model should not be able to grant itself authority by emitting a plausible field.
Alternative considered
Accept a free-form plan and filter approval language after generation.
Trade-off
The provider can fill fewer fields, but the schema itself prevents an approval transition from entering through model output.

What a pass means

The recorded checks exercise permission boundaries and workflow-state behavior. The 120 synthetic orders also show the intended branch distribution: 50 stop at deterministic rules and 70 reach the review state.

Repeating the same request produced one plan in the recorded test. That checks the idempotency contract; it does not establish production behavior under a distributed deployment.

05 / Scope

This is a backend control-flow prototype, not clinical software.

Current scope

Synthetic workflow contract

  • Hard rules before provider work
  • Typed draft and explicit workflow state
  • Role-restricted final decision
  • Idempotency, version, and audit receipts

Not established

Clinical or production use

  • No real patient data
  • No drug recommendation or clinical decision support
  • No autonomous approval
  • No distributed or production deployment claim

Proposed next validation

Inject failures across the full state path

Exercise malformed provider output, timeout, crash-before-commit, repeated submission, and unauthorized review against a frozen synthetic set, then verify zero duplicate side effects and complete audit events.

01 / Problem

Retrieval finds candidates. It does not prove a claim.

A search system can return a passage about the right protein, assay, or mechanism while the final answer changes a value, drops a unit, or borrows an experimental condition from somewhere else. The passage is relevant to the topic, but it does not support the sentence the system wants to release.

A citation by itself does not solve the problem. The workflow has to preserve which version of the source was searched, where the supporting text appears, what was measured, which unit was used, and under which conditions. If one of those elements does not match, the safe output is an explicit unsupported result.

Design question

How can a system let a model help with search and extraction without letting a fluent answer hide a missing source, unit, or experimental condition?

02 / System

Carry the evidence record through every stage.

Public surface

Static Evidence Console

The public repository uses public or labelled synthetic documents. Its generated console displays evidence cards, citations, risk flags, evaluation summaries, and failure summaries. The public retrieval path is deliberately small and deterministic.

The static page is a read-only artifact. It does not imply that the local API is deployed.

Local build

Backend test path

The local build separates keyword and vector retrieval, structured extraction, support checks, review state, and notifications across a backend stack using FastAPI, PostgreSQL with pgvector, Redis, and Docker Compose.

This is a local test build, not a production traffic or customer-deployment claim.

03 / Decisions

Three choices define the system boundary.

Decision 01

Preserve source identity before retrieval.

Why
The same document can have different versions, access conditions, or page locations. Plain extracted text is not enough to reconstruct the evidence later.
Alternative considered
Store only normalized text chunks and generate a citation after the answer is written.
Trade-off
Each chunk carries more metadata, but a reviewer can trace the result back to the exact source and location.

Decision 02

Separate retrieval from claim-support checking.

Why
Topic relevance does not guarantee that a passage supports the exact wording, number, unit, or experimental condition.
Alternative considered
Ask the model to answer directly from retrieved context and generate its own citation.
Trade-off
The workflow needs a structured claim schema and explicit checks, but missing evidence fails visibly instead of being filled from model memory.

Decision 03

Publish a static artifact before claiming a hosted backend.

Why
A public URL should show what is actually available. The console can expose the evidence contract without suggesting that a dynamic service is operating behind it.
Alternative considered
Present the local API, Dockerfile, or deployment blueprint as a live production service.
Trade-off
The public demo is less interactive, but its scope is accurate and the visible data bundle remains inspectable.

What the suite checks

The frozen synthetic set exercises the search, extraction, and validation behaviors represented in the build. A passing case means the expected result and failure route matched the defined fixture.

The public repository also keeps a small project-local gold set, failure taxonomy, and retrieval top-k ablation so a missed or unsupported result remains visible.

Missing supporting textReturn unsupported
Value or unit mismatchBlock release
Condition mismatchKeep for review
Supported structured claimSend to reviewer

05 / Scope

What the current result does and does not establish.

Current scope

Public artifact and local test build

  • Public or clearly labelled synthetic inputs
  • Fixed project-local evaluation
  • Inspectable static console and repository
  • Explicit unsupported and review routes

Not established

Production or scientific performance

  • No production deployment or documented customer use
  • No high-concurrency reliability claim
  • No clinical, legal, or regulatory determination
  • No open-ended scientific-accuracy claim

Proposed next validation

Held-out scientific questions

Evaluate the support-checking workflow on a held-out set of real public scientific questions reviewed by domain researchers, while keeping source version, passage, unit, and conditions in the review record.
